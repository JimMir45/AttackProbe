> **架构关联**

> | 4.4.4 节点协作流程 | 1.6 心跳与指令下发 | 指令队列结构、下发时序 |

### 1.1 设计目标

- 支持 54+ 节点（31省公司 + 23专业公司）的注册、管理与状态监控
- 节点状态实时感知，分级失联检测与告警
- 节点间安全通信（Token + mTLS）
- 支持节点上线/下线平滑过渡

### 1.2 核心设计决策

| 决策点 | 方案选择 | 备选方案 | 选择理由 |
|-------|---------|---------|---------|
| 通信模式 | 省公司主动连接集团 | 集团推送到省公司 | 穿越防火墙更简单，省公司出口策略更灵活 |
| 心跳机制 | 定时心跳 + 超时检测 | 长连接保活 | 降低连接维护成本，适应网络波动 |
| 认证方式 | Token + mTLS | 仅 Token | Token 用于应用层认证，mTLS 用于传输层加密 |
| 状态存储 | 数据库 + Redis 缓存 | 仅数据库 | 心跳频繁（30s/次），缓存减轻数据库压力 |
| 节点标识 | 语义化字符串 | UUID | province_beijing 比 UUID 更便于运维排查 |
| 配置下发 | 心跳响应携带指令 | 独立推送通道 | 复用心跳通道，无需额外维护长连接 |

### 1.4 失联检测算法

```
参数定义：
  heartbeat_interval    = 30s     // 心跳间隔
  offline_threshold     = 3       // 离线判定（连续miss次数）
  disconnected_threshold = 10     // 失联判定（连续miss次数）
  alert_threshold       = 1       // 告警判定（连续miss次数）

数据结构：
  NodeHeartbeatState {
    node_id:         string       // 节点标识
    last_heartbeat:  timestamp    // 最后心跳时间
    miss_count:      int          // 连续miss次数
    current_status:  enum         // 当前状态
    status_since:    timestamp    // 状态持续起始时间
  }

检测流程（每 heartbeat_interval 执行一次）：
  FOR each registered_node:
    elapsed = now() - node.last_heartbeat

    IF elapsed < heartbeat_interval * 1.5:
      // 正常心跳范围（含网络抖动容差）
      node.miss_count = 0
      IF node.current_status != ONLINE:
        transition(node, ONLINE)
        LOG("节点恢复在线", node_id, was=node.current_status)
    ELSE:
      node.miss_count += 1

      IF node.miss_count >= disconnected_threshold:
        IF node.current_status != DISCONNECTED:
          transition(node, DISCONNECTED)
          ALERT(level=CRITICAL, "节点失联", node_id, duration=elapsed)

      ELSE IF node.miss_count >= offline_threshold:
        IF node.current_status != OFFLINE:
          transition(node, OFFLINE)
          ALERT(level=WARNING, "节点离线", node_id, miss=node.miss_count)

      ELSE IF node.miss_count >= alert_threshold:
        ALERT(level=INFO, "节点心跳延迟", node_id, miss=node.miss_count)

transition(node, new_status):
  old_status = node.current_status
  node.current_status = new_status
  node.status_since = now()

  // 持久化到数据库
  UPDATE node SET status = new_status, updated_at = now()
  INSERT node_status_log (node_id, old_status, new_status, changed_at)

  // 更新 Redis 缓存
  REDIS.SET("node:status:{node_id}", new_status, TTL=300s)
```

### 1.7 节点数据缓存策略

```
缓存层级设计：

  L1: 应用内存缓存（进程内）
    - 节点列表（全量），TTL = 60s，定时刷新
    - 用于心跳处理时快速验证 node_id 有效性
    - 数据结构：map[node_id] → NodeBasicInfo

  L2: Redis 缓存
    - 节点状态：key = "node:status:{node_id}"，TTL = 300s
    - 节点心跳：key = "node:heartbeat:{node_id}"，TTL = 120s
    - 指令队列：key = "node:commands:{node_id}"，无 TTL（指令自带过期时间）
    - 数据结构：Hash / String

  L3: PostgreSQL
    - 完整节点信息，心跳数据异步批量写入
    - 状态变更实时写入

  读取策略：
    心跳处理 → L1 验证 → L2 状态查询 → 响应
    详情查询 → L2 缓存 → L3 数据库（miss 时回填 L2）
    列表查询 → L3 数据库（带分页），L2 缓存 summary 统计

  写入策略：
    心跳数据 → L2 实时写入 → L3 异步批量写入（5s 聚合）
    状态变更 → L2 + L3 同步写入
    指令下发 → L2 队列 LPUSH
```

### 2.1 设计目标

- 支持三种部署模式（在线/离线/容器），统一管理接口
- 轻量化 Agent 设计，最小化 Agent 侧复杂度
- 基于容量的智能任务分配
- 离线场景下的数据完整性保障

### 2.2 核心设计决策

| 决策点 | 方案选择 | 备选方案 | 选择理由 |
|-------|---------|---------|---------|
| 任务获取 | Agent 主动拉取（Pull） | 节点推送（Push） | Agent 无需暴露端口，穿透防火墙更简单，网络策略要求低 |
| 执行器集成 | Agent 内置执行器 | Agent 调用远程执行器 | 减少网络依赖，离线场景可用，延迟更低 |
| 结果上报 | 批量上报（阈值+时间） | 单条上报 | 减少网络请求，单条结果 ~2KB，批量 50 条 ~100KB，开销可控 |
| 离线包格式 | tar.gz + JSON manifest | 数据库备份 | 人可读，便于审计和调试，跨平台兼容 |
| 心跳间隔 | 10s（Agent级） | 30s（与节点相同） | Agent 更靠近目标，需要更快的状态感知 |
| 容量控制 | Agent 自报容量 | 节点集中调度 | Agent 最了解自身负载，自报更准确 |

### 2.4 任务分配算法

```
任务分配发生在 Agent 拉取任务时（Pull 模式）。

输入：
  agent_request = {
    agent_id:       "agent_dmz_01",
    capacity:       10,                // 可接收任务数
    executor_types: [1, 2],            // 支持的执行器类型
    current_jobs:   ["job_001"]        // 当前执行中（去重用）
  }

  pending_jobs: PriorityQueue          // 节点的待分配任务队列

输出：
  assigned_jobs: []Job                 // 分配给该 Agent 的任务列表

分配算法：
  1. 验证 Agent 身份和状态
     IF agent.status NOT IN (ONLINE, IDLE, EXECUTING):
       RETURN empty  // 异常 Agent 不分配任务

  2. 计算实际可分配数量
     actual_capacity = MIN(agent_request.capacity, MAX_BATCH_SIZE)
     // MAX_BATCH_SIZE = 20，防止单次分配过多

  3. 从优先级队列中匹配任务
     assigned = []
     FOR job IN pending_jobs.sorted_by(priority DESC, created_at ASC):
       // 跳过已在执行的任务
       IF job.job_id IN agent_request.current_jobs:
         CONTINUE

       // 检查执行器兼容性
       IF job.executor_type NOT IN agent_request.executor_types:
         CONTINUE

       // 检查网络区域匹配
       IF job.target.network_zone != agent.network_zone:
         IF NOT is_cross_zone_allowed(agent, job.target):
           CONTINUE

       assigned.APPEND(job)
       pending_jobs.REMOVE(job)

       IF LEN(assigned) >= actual_capacity:
         BREAK

  4. 标记任务状态
     FOR job IN assigned:
       job.status = DISPATCHED
       job.assigned_to = agent_id
       job.dispatched_at = now()

  RETURN assigned

优先级权重计算：
  priority_score = task.priority_weight          // 紧急=100, 高=80, 普通=50, 低=20
                 + age_bonus(job.created_at)      // 等待越久优先级越高，每小时+5
                 + retry_penalty(job.retry_count) // 重试次数越多优先级越低，每次-10
```

### 2.7 容量控制与过载保护

```
容量模型：

  Agent 容量 = max_concurrent - current_running

  示例：
    Agent 配置 max_concurrent = 20
    当前运行 current_running = 15
    可用容量 capacity = 5

  节点调度约束：
    分配给 Agent 的任务数 ≤ capacity
    如果所有 Agent 容量为 0，任务排队等待

过载保护：

  1. Agent 级别
     • 拉取时声明 capacity，节点不会超分配
     • 执行中任务超过 max_concurrent 的 80%，降低拉取频率
     • CPU > 90% 或 Memory > 85%，暂停拉取新任务

  2. 节点级别
     • 所有 Agent 容量总和 < 待分配任务数时，任务排队
     • 队列长度 > 1000，拒绝新任务创建
     • 监控 Agent 负载分布，避免热点

  3. 全网级别
     • 集团下发任务时，根据各节点上报的容量评估可行性
     • 容量不足的节点标记为 "部分执行"
```

- 用例库全网统一（集团→省公司单向同步）
- 结果数据可汇聚（省公司→集团上报）
- 网络中断可恢复（断点续传）
- 数据一致性保障（校验+重试）

### 3.2 核心设计决策

| 决策点 | 方案选择 | 备选方案 | 选择理由 |
|-------|---------|---------|---------|
| 同步模式 | 增量同步为主 | 全量同步 | 25000+ 用例全量同步耗时过长（约 50MB） |
| 版本标识 | 日期版本号 | 自增序列 | 直观，便于理解和排查（2026.01.29 vs #12345） |
| 冲突处理 | 集团覆盖省公司 | 合并策略 | 用例库集团权威，不存在双写冲突 |
| 断点续传 | 检查点 + 批次号 | 文件偏移量 | 批次号更直观，便于审计和问题排查 |
| 数据压缩 | gzip（用例>100条时） | 不压缩 | 用例 JSON 压缩率约 70%，节省带宽 |
| 变更粒度 | 用例级增量 | 字段级增量 | 用例作为原子单元，字段级增量过于复杂 |

### 3.4 用例版本管理算法

```
版本号格式：YYYY.MM.DD[.patch]
  示例：2026.01.29, 2026.01.29.1（同日多次发布）

版本链：
  2026.01.20 → 2026.01.25 → 2026.01.28 → 2026.01.29

变更追踪：
  每条用例包含：
    - case_id:       "BC-FW-001"       // 用例唯一标识
    - case_version:  "1.2.0"           // 用例自身版本（语义化版本）
    - sync_version:  "2026.01.29"      // 所属同步版本
    - operation:     "add|update|delete"// 操作类型
    - checksum:      "sha256:abc..."   // 内容校验和

增量同步算法：

  INPUT:
    node_current_version: "2026.01.28"   // 省公司当前版本
    latest_version:       "2026.01.29"   // 集团最新版本

  PROCESS:
    1. 查询变更集
       changes = SELECT * FROM case_changelog
                 WHERE sync_version > node_current_version
                 ORDER BY sync_version ASC, case_id ASC

    2. 合并同一用例的多次变更
       // 如果同一 case_id 在多个版本中都有变更，只保留最终状态
       merged = {}
       FOR change IN changes:
         IF change.case_id IN merged:
           // 后续操作覆盖前序操作
           // 特殊情况：add + delete = 无操作（省公司跳过）
           IF merged[change.case_id].operation == "add" AND change.operation == "delete":
             merged.REMOVE(change.case_id)
           ELSE:
             merged[change.case_id] = change
         ELSE:
           merged[change.case_id] = change

    3. 分批返回
       result = merged.values().sorted_by(case_id)
       RETURN paginate(result, offset, batch_size)

  OUTPUT:
    cases: [{case_id, operation, content, checksum}, ...]
    has_more: boolean

省公司应用变更：
  FOR case IN received_cases:
    SWITCH case.operation:
      "add":
        INSERT INTO local_cases (case_id, ...) VALUES (...)
      "update":
        UPDATE local_cases SET ... WHERE case_id = case.case_id
      "delete":
        UPDATE local_cases SET status = "deprecated" WHERE case_id = case.case_id
        // 软删除，保留历史记录

    // 验证校验和
    IF sha256(case.content) != case.checksum:
      LOG_ERROR("校验和不匹配", case_id)
      MARK_FOR_RETRY(case)
```

### 3.6 同步冲突处理

```
原则：集团数据具有最高优先级，省公司本地修改会被覆盖。

冲突场景与处理：

  场景 1：省公司本地修改了用例（自定义用例除外）
    处理：同步时集团版本覆盖本地版本
    保护：自定义用例（source=custom）不参与同步，不会被覆盖

  场景 2：用例被集团标记为废弃，但省公司正在使用
    处理：
      - 标记用例为 deprecated
      - 不立即删除，正在运行的任务继续执行
      - 新建任务时自动过滤 deprecated 用例
      - 30 天后归档

  场景 3：同步过程中，省公司重启
    处理：
      - 基于 checkpoint 断点续传
      - 已同步的部分不受影响
      - 未同步的部分重新拉取

  场景 4：版本跳跃（省公司长期离线，跨多个版本）
    处理：
      - 增量同步合并所有缺失版本的变更
      - 如果缺失版本过多（>10个版本），建议全量同步
      - 全量同步 API: POST /sync/case/pull?mode=full
```

```
  │ sync_delay_seconds  │ 同步延迟（最新版本 - 节点版本的时间差）  │
  │ sync_failure_count  │ 同步失败次数（连续）                     │
  │ sync_batch_duration │ 单批同步耗时                             │
```

### 4.4 Nuclei 执行器详细设计

```
Nuclei 集成方式：Go 库调用（非 CLI 子进程）

调用流程：
  1. 模板加载
     - 启动时从 cases/ 目录加载所有 .yaml 模板到内存
     - 按 case_id → template 建立索引
     - 监听文件变更，热更新模板缓存
     - 模板数量：~15000 个（60% × 25000）

  2. 执行流程
     INPUT: target, case

     a. 从缓存获取模板
        template = template_cache.get(case.case_id)
        IF template == nil:
          RETURN Result{status=ERROR, reason="模板未找到"}

     b. 构建执行选项
        options = NucleiOptions{
          Templates:       [template],
          Targets:         [target.endpoint],
          Timeout:         case.config.timeout,
          Retries:         case.config.retries,
          RateLimit:       50,  // 每秒请求限制
          BulkSize:        1,   // 单次执行一个目标
          CustomHeaders:   {"X-Attack-ID": trace_id},
        }

     c. 执行
        engine = nuclei.NewEngine(options)
        results = engine.ExecuteWithCallback(func(event){
          // 收集请求/响应详情
          capture_request(event)
          capture_response(event)
        })

        RETURN Result{

     - 50 个 Worker goroutine
     - 共享模板缓存（只读，无锁竞争）
```

### 4.7 执行结果判定逻辑

```
执行器返回 raw result 后，需要统一判定攻击是否"成功"（即防护是否失败）。

判定流程：
  INPUT: execution_result（执行器原始结果）
  OUTPUT: judge_result（判定结果）

  Step 1: 执行状态判定
    IF execution.status == TIMEOUT:
      RETURN {result=UNCERTAIN, reason="执行超时", confidence=0.30}
    IF execution.status == ERROR:
      RETURN {result=UNCERTAIN, reason="执行器错误", confidence=0.10}

  Step 2: Nuclei 结果判定
    IF executor_type == NUCLEI:
      IF nuclei.matched == true:
        // Nuclei 匹配成功 = 漏洞存在 = 防护失败
        RETURN {result=false, reason="Nuclei模板匹配成功", confidence=0.95}
      ELSE:
        // Nuclei 未匹配 = 防护成功（或用例不适用）
        RETURN {result=true, reason="Nuclei模板未匹配", confidence=0.90}

  Step 3: Python 结果判定
    IF executor_type == PYTHON:
      // Python 脚本自行判定，返回 matched 字段
      IF python.result.matched == true:
        RETURN {result=false, reason=python.result.reason, confidence=0.85}
      ELSE:
        RETURN {result=true, reason=python.result.reason, confidence=0.85}

  Step 4: 日志关联增强判定（如果启用）
    IF log_correlation.enabled:
      log_result = correlate_logs(trace_id, time_window)
      // 根据日志关联结果调整置信度
      IF log_result.matched:
        judge.confidence = MIN(judge.confidence + 0.05, 1.0)
        judge.reason += "，安全设备已记录"
      ELSE:
        judge.reason += "，安全设备未记录"

  RETURN judge_result

置信度说明：
  ┌─────────────────┬───────────────────────────────────────────────────┐
  │ 置信度范围       │ 含义                                              │
  ├─────────────────┼───────────────────────────────────────────────────┤
  │ 0.90 - 1.00     │ 高置信度，判定结果可靠                            │
  │ 0.70 - 0.89     │ 中置信度，判定可能存在误差                        │
  │ 0.50 - 0.69     │ 低置信度，建议人工复核                            │
  │ < 0.50          │ 不可靠，标记为 UNCERTAIN                          │
  └─────────────────┴───────────────────────────────────────────────────┘
```

### 5.5 日志关联匹配算法

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          关联匹配算法                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  输入：                                                                      │
│    attack_record = {                                                        │
│      trace_id:     "atk-20260129-uuid001",                                  │
│      executed_at:  "2026-01-29T10:00:00Z",                                 │
│      source_ip:    "10.0.1.50",       // Agent 或节点 IP                    │
│      target_ip:    "192.168.1.100",                                        │
│      target_port:  443,                                                    │
│      protocol:     "https",                                                │
│      case_id:      "BC-FW-001",                                            │
│      payload_sig:  ["sql_injection", "union select"],                      │
│    }                                                                        │
│                                                                             │
│  配置参数：                                                                  │
│    time_window      = 60s      // 时间窗口                                  │
│    weight_five_tuple = 0.40    // 五元组权重                                │
│    weight_trace_id   = 0.20    // TraceID 权重                              │
│    weight_payload    = 0.40    // Payload 特征权重                          │
│    match_threshold   = 0.60    // 匹配阈值                                  │
│                                                                             │
│  匹配流程：                                                                  │
│                                                                             │
│  Step 1: 时间窗口筛选                                                        │
│    time_start = attack_record.executed_at - 5s    // 提前量                 │
│    time_end   = attack_record.executed_at + time_window                    │
│                                                                             │
│    candidate_logs = ES_QUERY(                                               │
│      index = "security-logs-*",                                             │
│      filter = {                                                             │
│        range: {"@timestamp": {gte: time_start, lte: time_end}}             │
│      },                                                                     │
│      size = 1000                                                            │
│    )                                                                        │
│                                                                             │
│  Step 2: 多维度评分                                                          │
│    FOR each log IN candidate_logs:                                          │
│      score = 0.0                                                            │
│      matched_dims = []                                                      │
│                                                                             │
│      // 五元组匹配                                                           │
│      five_tuple_score = 0                                                   │
│      IF log.source.ip == attack_record.source_ip:                           │
│        five_tuple_score += 0.25                                             │
│      IF log.destination.ip == attack_record.target_ip:                      │
│        five_tuple_score += 0.35                                             │
│      IF log.destination.port == attack_record.target_port:                  │
│        five_tuple_score += 0.25                                             │
│      IF normalize_protocol(log.network.protocol) == attack_record.protocol:│
│        five_tuple_score += 0.15                                             │
│      score += five_tuple_score * weight_five_tuple                          │
│      IF five_tuple_score > 0.5:                                             │
│        matched_dims.append("five_tuple")                                    │
│                                                                             │
│      // TraceID 匹配（最可靠）                                               │
│      IF attack_record.trace_id IN log.message:                              │
│        score += 1.0 * weight_trace_id                                       │
│        matched_dims.append("trace_id")                                      │
│                                                                             │
│      // Payload 特征匹配                                                     │
│      payload_match = 0                                                      │
│      FOR sig IN attack_record.payload_sig:                                  │
│        IF sig IN log.rule.category OR sig IN log.message:                   │
│          payload_match += 1                                                 │
│      payload_score = payload_match / LEN(attack_record.payload_sig)         │
│      score += payload_score * weight_payload                                │
│      IF payload_score > 0.5:                                                │
│        matched_dims.append("payload_signature")                             │
│                                                                             │
│      log.match_score = score                                                │
│      log.matched_dims = matched_dims                                        │
│                                                                             │
│  Step 3: 结果判定                                                            │
│    matched_logs = [l for l in candidate_logs if l.match_score >= match_threshold]
│    matched_logs.sort_by(match_score, DESC)                                  │
│                                                                             │
│    IF LEN(matched_logs) == 0:                                               │
│      RETURN {                                                               │
│        matched: false,                                                      │
│        reason: "时间窗口内未找到匹配日志",                                    │
│        searched_logs: LEN(candidate_logs),                                  │
│        best_score: MAX(candidate_logs.match_score) or 0                     │
│      }                                                                      │
│    ELSE:                                                                    │
│      best_match = matched_logs[0]                                           │
│      RETURN {                                                               │
│        matched: true,                                                       │
│        match_score: best_match.match_score,                                 │
│        matched_dims: best_match.matched_dims,                               │
│        device_type: best_match.observer.type,                               │
│        device_action: best_match.event.action,                              │
│        log_id: best_match._id,                                              │
│        log_time: best_match.@timestamp,                                     │
│        searched_logs: LEN(candidate_logs),                                  │
│        all_matches: LEN(matched_logs)                                       │
│      }                                                                      │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 6.1 设计目标

- 支持单任务 10,000+ 用例执行
- 支持任务暂停/恢复/取消
- 支持优先级调度（紧急任务插队）
- 全网任务进度实时可见
- 执行结果实时流式上报

### 6.2 核心设计决策

| 决策点 | 方案选择 | 备选方案 | 选择理由 |
|-------|---------|---------|---------|
| 任务队列 | Redis Stream | RabbitMQ | 轻量级，支持消费者组，ACK 机制完善 |
| 调度模式 | 分布式调度 | 集中调度 | 节点独立调度本节点任务，集团不参与执行 |
| 进度同步 | Redis 实时更新 | 数据库轮询 | 低延迟，支持高频更新 |
| 结果存储 | 批量写入 | 单条写入 | 减少数据库 IO，提升吞吐 |
| 超时控制 | Context + Watchdog | 仅 Context | Watchdog 兜底防止僵尸任务 |
| 失败重试 | 指数退避 | 固定间隔 | 避免瞬时高负载，对后端友好 |

### 6.5 优先级调度算法

```
任务优先级决定执行顺序，支持紧急任务插队。

优先级队列实现：
  使用 Redis Sorted Set，score = priority_score

  Key: task_queue:{node_id}
  Score: 优先级分数（越小越优先）
  Member: job_id

优先级分数计算：
  priority_score = base_priority              // 基础优先级
                 - urgency_bonus              // 紧急加成
                 + age_penalty                // 等待惩罚
                 + retry_penalty              // 重试惩罚

  参数定义：
    base_priority:
      紧急(urgent)  = 1000
      高(high)      = 2000
      普通(normal)  = 3000
      低(low)       = 4000

    urgency_bonus:
      全网任务(scope=group_wide) = 500
      护网任务(tag=hw)           = 300

    age_penalty:
      penalty = (now - created_at).minutes * 0.1
      // 等待时间越长，分数越低（优先级越高）
      max_penalty = 500

    retry_penalty:
      penalty = retry_count * 100
      // 重试次数越多，优先级越低
      max_penalty = 300

调度示例：
  Job A: 紧急 + 全网 + 等待10分钟 = 1000 - 500 + 1 = 501
  Job B: 普通 + 本省 + 等待60分钟 = 3000 - 0 + 6 = 3006
  Job C: 高 + 全网 + 等待5分钟 + 重试1次 = 2000 - 500 + 0.5 + 100 = 1600.5

  执行顺序：A (501) → C (1600.5) → B (3006)
```

### 6.6 进度跟踪机制

```
进度数据使用 Redis 实时更新，支持高频查询。

数据结构：
  // 任务级进度
  Key: task:progress:{task_id}
  Type: Hash
  Fields:
    total_jobs:     int    // 总 Job 数
    completed_jobs: int    // 已完成数
    running_jobs:   int    // 执行中数
    pending_jobs:   int    // 待执行数
    success_count:  int    // 成功数
    failed_count:   int    // 失败数
    error_count:    int    // 错误数
    started_at:     string // 开始时间
    updated_at:     string // 更新时间
    rate_per_min:   float  // 当前执行速率

  // 节点级进度（全网任务）
  Key: task:progress:{task_id}:nodes
  Type: Hash
  Fields:
    {node_id}: JSON {completed, total, percent, status}

  // Agent 级进度
  Key: task:progress:{task_id}:agents
  Type: Hash
  Fields:
    {agent_id}: JSON {completed, total, running, last_update}

进度更新流程：
  1. Worker 完成一个 Job
     → HINCRBY task:progress:{task_id} completed_jobs 1
     → HINCRBY task:progress:{task_id} success_count 1 (或 failed_count)
     → HSET task:progress:{task_id} updated_at {now}

  2. 每 10 秒计算速率
     → rate = (current_completed - prev_completed) * 6

  3. 进度百分比计算
     → percent = completed_jobs / total_jobs * 100

  4. ETA 预估
     → remaining = total_jobs - completed_jobs
     → eta_seconds = remaining / rate_per_min * 60

进度查询 API 响应示例：
  {
    "task_id": 100,
    "status": "running",
    "progress": {
      "total_jobs": 15000,
      "completed_jobs": 7500,
      "running_jobs": 50,
      "pending_jobs": 7450,
      "percent": 50.0
    },
    "statistics": {
      "success_count": 6900,
      "failed_count": 500,
      "error_count": 100,
      "success_rate": 92.0
    },
    "timing": {
      "started_at": "2026-01-29T10:05:00Z",
      "elapsed_seconds": 900,
      "rate_per_minute": 500,
      "eta_seconds": 900,
      "estimated_finish_at": "2026-01-29T10:35:00Z"
    }
  }
```

### 6.7 超时与异常处理

```
超时控制采用多层机制，确保任务不会无限期挂起。

超时层级：
  ┌────────────────────────────────────────────────────────────────────────┐
  │ 层级       │ 超时时间    │ 处理方式                                    │
  ├────────────────────────────────────────────────────────────────────────┤
  │ Job 级别   │ 30-300s    │ Context.WithTimeout 取消执行                │
  │            │ (可配置)    │ 标记为 TIMEOUT，记录已执行时长               │
  ├────────────────────────────────────────────────────────────────────────┤
  │ Task 级别  │ 24h        │ 定时检查 Watchdog                           │
  │            │ (默认)      │ 超时后标记为 PARTIAL，统计完成情况           │
  ├────────────────────────────────────────────────────────────────────────┤
  │ Worker 级别│ 60s        │ 心跳检测，无响应则重启 Worker                │
  │            │ (健康检查)  │ 当前 Job 放回队列                           │
  └────────────────────────────────────────────────────────────────────────┘

异常处理策略：
  ┌────────────────────────────────────────────────────────────────────────┐
  │ 异常类型        │ 重试策略           │ 最终处理                        │
  ├────────────────────────────────────────────────────────────────────────┤
  │ 网络超时        │ 3次，指数退避      │ 标记 TIMEOUT，记录原因          │
  │                │ (1s, 2s, 4s)       │                                 │
  ├────────────────────────────────────────────────────────────────────────┤
  │ 目标不可达      │ 不重试            │ 标记 ERROR，目标可能已下线        │
  ├────────────────────────────────────────────────────────────────────────┤
  │ 执行器错误      │ 2次               │ 标记 ERROR，记录堆栈信息          │
  ├────────────────────────────────────────────────────────────────────────┤
  │ 结果解析失败    │ 不重试            │ 标记 ERROR，保存原始输出          │
  ├────────────────────────────────────────────────────────────────────────┤
  │ Agent 离线      │ 等待恢复或转移    │ Job 放回队列，等待其他 Agent      │
  └────────────────────────────────────────────────────────────────────────┘

Watchdog 定时任务：
  周期：每 5 分钟执行
  检查内容：
    1. 运行中任务超过 24 小时 → 标记 PARTIAL
    2. Job 分配后 10 分钟无进度 → 放回队列
    3. Worker 心跳超时 → 重启 Worker
    4. 结果上报队列积压 > 10000 → 告警
```

### 7.4 索引策略

```
索引设计原则：
  1. 高频查询字段必建索引
  2. 组合索引遵循最左前缀原则
  3. 低基数字段（如 status）使用部分索引
  4. JSONB 字段使用 GIN 索引
  5. 大表考虑分区后的本地索引

核心查询场景与索引映射：
  ┌────────────────────────────────────────────────────────────────────────┐
  │ 查询场景                      │ 使用索引                               │
  ├────────────────────────────────────────────────────────────────────────┤
  │ 任务列表（状态筛选+分页）     │ idx_task_status + idx_task_created     │
  │ 任务进度查询                  │ idx_job_task + idx_job_status          │
  │ 用例搜索                     │ idx_case_name_gin (全文) + idx_case_*   │
  │ 执行结果（任务维度）          │ idx_result_task + 分区裁剪              │
  │ 执行结果（TraceID 查询）      │ idx_result_trace                       │
  │ 节点心跳检查                  │ idx_node_heartbeat                     │
  │ Agent 任务分配                │ idx_agent_status + idx_agent_node      │
  │ 日志关联查询                  │ ES 索引（见日志闭环设计）               │
  └────────────────────────────────────────────────────────────────────────┘

部分索引示例（减少索引大小）：
  -- 只索引未完成的任务
  CREATE INDEX idx_task_pending ON task(created_at DESC)
    WHERE status IN (1,2,3,4,5);

  -- 只索引在线 Agent
  CREATE INDEX idx_agent_online ON agent(node_id, status)
    WHERE status IN (1,3,4);
```

```

  task_result 表（按时间范围分区）：

    │ 分区名                │ 时间范围                  │ 存储策略       │
    ├────────────────────────────────────────────────────────────────────┤
    │ task_result_2026_01  │ 2026-01-01 ~ 2026-02-01  │ 热数据，SSD    │
    │ task_result_2026_02  │ 2026-02-01 ~ 2026-03-01  │ 热数据，SSD    │
    │ ...                  │ ...                      │ ...           │
    │ task_result_2025_08  │ 6个月前                  │ 温数据，HDD    │
    │ task_result_2025_07  │ 7个月前                  │ 归档，压缩     │
    └────────────────────────────────────────────────────────────────────┘

  分区维护脚本（定时任务）：
    1. 每月 1 日 00:00 自动创建下月分区
    2. 每月 1 日检查 6 个月前分区，迁移到 HDD 表空间
    3. 每月 1 日检查 180 天前分区，导出归档后删除
```

### 9.1 设计目标

- 建立统一的防护能力评分模型，量化安全防护效果
- 支持全网横向对比，识别防护短板和最佳实践
- 自动生成多层次报告（全网/对比/本节点）
- 评分可追溯、可解释、可配置

### 9.2 核心设计决策

| 决策点 | 方案选择 | 备选方案 | 选择理由 |
|-------|---------|---------|---------|
| 评分模型 | 多维加权模型 | 单一指标 | 安全能力是多维度的，单一指标无法全面反映 |
| 评分基准 | 百分制 + 等级映射 | 仅等级 | 百分制便于精确对比，等级便于直观理解 |
| 横向对比 | 实时计算 + 缓存 | 定时批量计算 | 支持按需查询，缓存降低计算开销 |
| 报告生成 | 异步生成 + 模板渲染 | 同步生成 | 大型报告耗时较长，异步避免阻塞 |
| 报告格式 | HTML/PDF/Word 多格式 | 仅 PDF | 不同场景需求不同，HTML 便于在线查看 |
| 评分权重 | 可配置 | 固定权重 | 不同组织对安全维度关注点不同 |

### 9.4 评分计算算法

```
评分计算服务（ScoreService）

输入：
  task_result: 任务执行结果集合
  weight_config: 权重配置（可选，使用默认权重）

输出：
  score_result: {
    total_score:     float,      // 总分（0-100）
    grade:           string,     // 等级（A/B/C/D/E）
    dimension_scores: {},        // 各维度得分
    details:         {},         // 评分明细
  }

计算流程：

  Step 1: 计算防护成功率（40%）
    total_attacks = COUNT(task_result WHERE status IN (success, failed))
    blocked_attacks = COUNT(task_result WHERE judge_result = true)

    IF total_attacks == 0:
      protection_rate = 0
    ELSE:
      protection_rate = blocked_attacks / total_attacks * 100

    protection_score = protection_rate

  Step 2: 计算日志闭环完成度（25%）
    log_enabled_attacks = COUNT(task_result WHERE log_correlation.enabled = true)

    // 四环节评分：attack=0, detection=40, alert=35, logging=25
    stage_weights = {detection: 40, alert: 35, logging: 25}

    total_stage_score = 0
    FOR result IN log_enabled_attacks:
      stage_score = 0
      IF result.verification_path.detection: stage_score += 40
      IF result.verification_path.alert:     stage_score += 35
      IF result.verification_path.logging:   stage_score += 25
      total_stage_score += stage_score

    IF log_enabled_attacks == 0:
      log_loop_score = 0
    ELSE:
      log_loop_score = total_stage_score / log_enabled_attacks

  Step 3: 计算用例覆盖度（20%）
    // 按二级分类统计
    executed_categories = DISTINCT(task_result.case.sub_category)
    total_categories = DISTINCT(all_cases.sub_category WHERE enabled = true)

    coverage_rate = LEN(executed_categories) / LEN(total_categories) * 100
    coverage_score = coverage_rate

  Step 4: 计算响应时效性（10%）
    // 基于检测到告警的时间差
    response_times = []
    FOR result IN task_result WHERE log_correlation.matched:
      IF result.verification_path.alert:
        response_time = result.log_correlation.alert_time - result.executed_at
        response_times.APPEND(response_time)

    IF LEN(response_times) == 0:
      timeliness_score = 0
    ELSE:
      avg_response_ms = AVG(response_times)
      // 响应越快得分越高：<1s=100, <5s=80, <30s=60, <60s=40, ≥60s=20
      timeliness_score = CASE
        WHEN avg_response_ms < 1000   THEN 100
        WHEN avg_response_ms < 5000   THEN 80
        WHEN avg_response_ms < 30000  THEN 60
        WHEN avg_response_ms < 60000  THEN 40
        ELSE 20
      END

  Step 5: 计算资产覆盖度（5%）
    tested_assets = DISTINCT(task_result.target_id)
    total_assets = COUNT(targets WHERE status = enabled)

    asset_coverage = LEN(tested_assets) / total_assets * 100
    asset_score = asset_coverage

  Step 6: 计算总分
    weights = weight_config OR default_weights
    total_score = protection_score * weights.protection      // 40%
                + log_loop_score * weights.log_loop          // 25%
                + coverage_score * weights.coverage          // 20%
                + timeliness_score * weights.timeliness      // 10%
                + asset_score * weights.asset                // 5%

    total_score = ROUND(total_score, 2)

  Step 7: 映射等级
    grade = CASE
      WHEN total_score >= 90 THEN 'A'
      WHEN total_score >= 80 THEN 'B'
      WHEN total_score >= 70 THEN 'C'
      WHEN total_score >= 60 THEN 'D'
      ELSE 'E'
    END

  RETURN {
    total_score,
    grade,
    dimension_scores: {
      protection:  {score: protection_score, weight: 0.40, weighted: protection_score * 0.40},
      log_loop:    {score: log_loop_score, weight: 0.25, weighted: log_loop_score * 0.25},
      coverage:    {score: coverage_score, weight: 0.20, weighted: coverage_score * 0.20},
      timeliness:  {score: timeliness_score, weight: 0.10, weighted: timeliness_score * 0.10},
      asset:       {score: asset_score, weight: 0.05, weighted: asset_score * 0.05}
    },
    details: {
      total_attacks,
      blocked_attacks,
      log_enabled_attacks,
      executed_categories: LEN(executed_categories),
      avg_response_ms,
      tested_assets: LEN(tested_assets)
    }
  }
```

**横向对比算法：**

```
横向对比服务

输入：
  task_id:        int           // 任务ID
  comparison_type: string       // province | professional | region | all
  metrics:        []string      // 对比维度

输出：
  comparison_result: {
    rankings: [],               // 排名列表
    statistics: {},             // 统计数据
    analysis: {}                // 分析结论
  }

算法流程：

  Step 1: 获取参与节点
    IF comparison_type == "all":
      nodes = GET_ALL_NODES(task_id)
    ELSE IF comparison_type == "province":
      nodes = GET_NODES(task_id, node_type=2)
    ELSE IF comparison_type == "professional":
      nodes = GET_NODES(task_id, node_type=3)
    ELSE IF comparison_type == "region":
      nodes = GET_NODES(task_id, region=specified_region)

  Step 2: 计算各节点评分
    node_scores = []
    FOR node IN nodes:
      node_result = GET_TASK_RESULTS(task_id, node_id=node.id)
      score = ScoreService.calculate(node_result)
      node_scores.APPEND({
        node_id:   node.id,
        node_name: node.name,
        node_type: node.type,
        region:    node.region,
        score:     score,
        metrics:   EXTRACT_METRICS(score, metrics)
      })

  Step 3: 多维度排名
    rankings = {}
    FOR metric IN metrics:
      sorted_nodes = SORT(node_scores, by=metric, order=METRIC_ORDER[metric])
      FOR i, node IN enumerate(sorted_nodes):
        IF node.node_id NOT IN rankings:
          rankings[node.node_id] = {}
        rankings[node.node_id][metric] = {
          rank: i + 1,
          value: node.metrics[metric],
          percentile: (LEN(nodes) - i) / LEN(nodes) * 100
        }

  Step 4: 综合排名计算
    // 综合排名 = 各维度排名的加权平均
    FOR node_id IN rankings:
      weighted_rank = 0
      FOR metric IN metrics:
        weighted_rank += rankings[node_id][metric].rank * METRIC_WEIGHTS[metric]
      rankings[node_id].overall_rank = ROUND(weighted_rank)

    // 按综合排名排序
    final_rankings = SORT(rankings, by=overall_rank, order=ASC)

  Step 5: 统计分析
    statistics = {
      total_nodes:    LEN(nodes),
      avg_score:      AVG(node_scores.score.total_score),
      max_score:      MAX(node_scores.score.total_score),
      min_score:      MIN(node_scores.score.total_score),
      std_deviation:  STD(node_scores.score.total_score),
      by_grade: {
        A: COUNT(node_scores WHERE grade == 'A'),
        B: COUNT(node_scores WHERE grade == 'B'),
        C: COUNT(node_scores WHERE grade == 'C'),
        D: COUNT(node_scores WHERE grade == 'D'),
        E: COUNT(node_scores WHERE grade == 'E')
      }
    }

  Step 6: 生成分析结论
    top_performers = final_rankings[0:3]                    // 前三名
    needs_improvement = final_rankings[-3:]                 // 后三名

    // 识别共性问题
    common_weaknesses = []
    FOR metric IN metrics:
      below_avg_count = COUNT(nodes WHERE metric < statistics.avg[metric])
      IF below_avg_count > LEN(nodes) * 0.5:
        common_weaknesses.APPEND(metric)

    analysis = {
      top_performers: top_performers,
      needs_improvement: needs_improvement,
      common_weaknesses: common_weaknesses,
      recommendations: GENERATE_RECOMMENDATIONS(common_weaknesses)
    }

  RETURN {rankings: final_rankings, statistics, analysis}
```

**报告生成流程：**

```
报告生成服务（ReportService）

报告生成流程（异步）：

  Step 1: 创建报告任务
    report_job = {
      id:          generate_id(),
      task_id:     task_id,
      report_type: type,           // full | summary | comparison
      format:      format,         // pdf | html | word
      status:      "pending",
      created_at:  now(),
      created_by:  user_id
    }
    INSERT report_job INTO report_jobs

  Step 2: 数据收集（Worker 执行）
    data = {}

    // 基础数据
    data.task = GET_TASK(task_id)
    data.results = GET_TASK_RESULTS(task_id)
    data.score = ScoreService.calculate(data.results)

    // 全网/对比报告额外数据
    IF report_type IN ("full", "comparison"):
      data.comparison = ComparisonService.compare(task_id)
      data.historical = GET_HISTORICAL_SCORES(task_id, limit=6)

    // 更新进度
    UPDATE report_job SET progress = 30

  Step 3: 数据分析
    analysis = {}

    // 分类统计
    analysis.by_category = GROUP_BY(data.results, case.category)
    analysis.by_device = GROUP_BY(data.results, target.sub_type)
    analysis.by_risk_level = GROUP_BY(data.results, case.risk_level)

    // 失败分析
    failed_results = FILTER(data.results, judge_result=false)
    analysis.top_failed_cases = TOP(failed_results, 20, by=count)

    // 日志闭环分析
    analysis.log_loop = ANALYZE_LOG_LOOP(data.results)

    // 问题识别
    analysis.issues = IDENTIFY_ISSUES(data, analysis)
    analysis.recommendations = GENERATE_RECOMMENDATIONS(analysis.issues)

    UPDATE report_job SET progress = 60

  Step 4: 报告渲染
    template = GET_TEMPLATE(report_type, format)

    // 准备图表数据
    charts = {
      score_radar:      GENERATE_RADAR_CHART(data.score),
      trend_line:       GENERATE_TREND_CHART(data.historical),
      category_bar:     GENERATE_BAR_CHART(analysis.by_category),
      device_pie:       GENERATE_PIE_CHART(analysis.by_device),
      ranking_table:    GENERATE_TABLE(data.comparison.rankings),
      heatmap:          GENERATE_HEATMAP(data.comparison)      // 全网评分热力图
    }

    // 渲染报告
    report_content = RENDER(template, {
      data:     data,
      analysis: analysis,
      charts:   charts,
      metadata: {
        generated_at: now(),
        generated_by: user_id,
        version:      "v1.0"
      }
    })

    UPDATE report_job SET progress = 90

  Step 5: 导出与存储
    IF format == "pdf":
      file = PDF_EXPORT(report_content)
    ELSE IF format == "html":
      file = HTML_EXPORT(report_content)
    ELSE IF format == "word":
      file = DOCX_EXPORT(report_content)

    file_path = STORE_FILE(file, "reports/{task_id}/{report_id}.{format}")

    UPDATE report_job SET
      status = "completed",
      progress = 100,
      file_path = file_path,
      file_size = file.size,
      completed_at = now()

  Step 6: 通知
    IF job.notification.on_complete:
      NOTIFY(job.created_by, "报告已生成", file_path)

报告缓存策略：
  • 同一任务同一类型的报告缓存 24 小时
  • 任务结果更新后缓存失效
  • HTML 格式支持在线预览，无需下载
```

```sql
-- ============================================================
-- 评分记录表 (task_score)
-- ============================================================
CREATE TABLE task_score (
    id              BIGSERIAL PRIMARY KEY,
    task_id         BIGINT NOT NULL,
    node_id         VARCHAR(50) NOT NULL,           -- 评分所属节点

    -- 总分与等级
    total_score     DECIMAL(5,2) NOT NULL,          -- 0.00-100.00
    grade           CHAR(1) NOT NULL,               -- A/B/C/D/E

    -- 各维度得分
    protection_score    DECIMAL(5,2),               -- 防护成功率得分
    log_loop_score      DECIMAL(5,2),               -- 日志闭环得分
    coverage_score      DECIMAL(5,2),               -- 用例覆盖度得分
    timeliness_score    DECIMAL(5,2),               -- 响应时效性得分
    asset_score         DECIMAL(5,2),               -- 资产覆盖度得分

    -- 原始数据
    raw_data        JSONB,                          -- 评分计算的原始数据

    -- 权重配置（记录评分时使用的权重）
    weight_config   JSONB,

    -- 对比信息
    rank_in_task    INTEGER,                        -- 在本任务中的排名
    rank_change     INTEGER,                        -- 排名变化（与上次同类任务比较）

    scored_at       TIMESTAMP NOT NULL,
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    UNIQUE(task_id, node_id)
);

-- 索引
CREATE INDEX idx_score_task ON task_score(task_id);
CREATE INDEX idx_score_node ON task_score(node_id);
CREATE INDEX idx_score_grade ON task_score(grade);
CREATE INDEX idx_score_total ON task_score(total_score DESC);

-- ============================================================
-- 报告记录表 (report)
-- ============================================================
CREATE TABLE report (
    id              BIGSERIAL PRIMARY KEY,
    report_id       VARCHAR(50) NOT NULL UNIQUE,    -- rpt_20260129_001

    task_id         BIGINT NOT NULL,
    node_id         VARCHAR(50),                    -- null=全网报告

    -- 报告类型与格式
    report_type     VARCHAR(20) NOT NULL,           -- full | summary | comparison | node
    format          VARCHAR(10) NOT NULL,           -- pdf | html | word

    -- 报告内容配置
    sections        JSONB,                          -- 包含的章节
    options         JSONB,                          -- 生成选项

    -- 生成状态
    status          VARCHAR(20) DEFAULT 'pending',  -- pending | generating | completed | failed
    progress        INTEGER DEFAULT 0,              -- 0-100

    -- 文件信息
    file_path       VARCHAR(500),
    file_size       BIGINT,
    checksum        VARCHAR(100),

    -- 时间
    started_at      TIMESTAMP,
    completed_at    TIMESTAMP,
    expires_at      TIMESTAMP,                      -- 报告过期时间

    created_by      BIGINT,
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 索引
CREATE INDEX idx_report_task ON report(task_id);
CREATE INDEX idx_report_node ON report(node_id);
CREATE INDEX idx_report_type ON report(report_type);
CREATE INDEX idx_report_status ON report(status);
CREATE INDEX idx_report_created ON report(created_at DESC);

-- ============================================================
-- 评分权重配置表 (score_weight_config)
-- ============================================================
CREATE TABLE score_weight_config (
    id              BIGSERIAL PRIMARY KEY,
    config_name     VARCHAR(100) NOT NULL,
    description     TEXT,

    -- 权重配置
    weights         JSONB NOT NULL,                 -- {protection: 0.40, log_loop: 0.25, ...}

    -- 使用范围
    scope           VARCHAR(20) DEFAULT 'global',   -- global | node
    node_id         VARCHAR(50),                    -- scope=node 时指定

    -- 状态
    is_default      BOOLEAN DEFAULT FALSE,
    enabled         BOOLEAN DEFAULT TRUE,

    created_by      BIGINT,
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```
